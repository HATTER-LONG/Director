# 当前本地 H3 与 GPT Image 2.6

本页记录 2026-11-06 核对的部署能力，依据 Toonflow `listMediaProviders`、`data/providers/comfyH3.ts`、`data/providers/cpa.ts` 与 ComfyUI `object_info`。它是当前适配器的能力快照，不是模型全部能力或出片质量保证。供应商、工作流或版本变化时重查；同一会话未变的参数可复用，提交前仍核对当前节点和实际输入。

## 参考优先

默认用完整的人物、造型、场景和道具参考，加提示词说明取景、动作与终点。完整是足够交代本镜所需事实：人物全身与脸部细节、服装和持物，场景布局与必要反打，道具形制与状态；按镜头需要组合，不规定每镜都挂齐全部资产。不把人物参考摆成某一首尾姿态，不为锁帧删掉理解动作所需的信息。

参考图可以保持原画幅。多视图属于同一人物时明确绑定同一主体；标注与排版不进入成片。细节太小或多视图引起歧义时补清晰视图，不默认把完整参考裁成视频画框。起点和终点首先是分镜中的状态描述，关键帧图按需准备。

## GPT Image 2.6：当前 CPA 入口

- 供应商 `cpa`；实际模型 ID 为 `gpt-image-2.6`，另有 `gpt-image-2.6-flare`、`gpt-image-2.6-sunburst`。沿用用户选定 ID，不因名字相近自动替换。
- 当前仅开放 `1K`，比例为 `1:1`、`3:2`、`2:3`；每次 `n=1`。适配器的请求尺寸映射为 `1024×1024`、`1536×1024`、`1024×1536`，但实际回收文件可能不同；入库时读取文件宽高，不能把请求值当作已实测尺寸。不能把通用 API 的其他尺寸、透明背景或种子能力直接写成此节点可用参数。
- 无图走生成；有图走编辑，按实际顺序用自然语言说明每张图控制的身份、空间、材质等范围。H3 的 `<Picture N>` 不是此图片接口的参考语法。编辑说明“改什么、保持什么”；mask 只有节点确实暴露且已接入时才算有效。
- 质量选项为 `auto/low/medium/high`，输出为 `png/jpeg/webp`，以节点实际暴露字段为准。候选探索和最终资产可分别选合适质量，不强制每次最高质量。
- 人物和空间参考无需裁成 9:16。只有交付确需 9:16 构图帧时，先按 2:3 出图并预留取景余量，再按实际画面裁切；若实测为 1024×1536，居中 9:16 窗口为 864×1536，两侧各裁 80 px；其他尺寸重新计算。先检查头、手、道具和文字，不拉伸；裁不下就调整取景或编辑原图。

官方图像接口背景见 [Images API](https://developers.openai.com/api/reference/resources/images/methods/generate)；实际可提交范围以上述部署为准。

## H3：当前 comfyH3 入口

- `h3-quick` 与 `h3-enhanced` 使用 `MiniMaxH3ReferenceToVideo`。UI 的 `singleImage` 也是参考输入；不支持 `firstFrame/lastFrame` 端口，不能宣称严格 I2VA/FL2VA 或用参考图强制首尾帧对齐。有参考时按 Ref2VA 编译；无参考的 text 任务按文生格式编译。
- 最多 9 张图片、3 段视频、3 段独立音频。`<Picture N>`、`<Video N>`、`<Audio N>` 各类型分别从 1 编号，并与实际挂载顺序一致。当前适配器不展开 `{{ref N}}`。
- 完整参考说明什么应保持，动作正文说明怎么变化。构图、朝向和动作终点是生成目标，不能写成已被端口锁定的事实。不要为凑满槽位加入冲突造型或多余视图。
- 目标时长为整数 2–15 秒、24 fps，帧数向上对齐到 `17n+5`。设 `N = 24 × 目标秒数`，实际帧数为 `N + ((5-N) mod 17)`（余数取 0–16）。例如 5 秒为 124 帧，约 5.167 秒；15 秒为 362 帧，约 15.083 秒。剪辑镜长、提交目标秒数、实测素材时长分别记录；不为取整改故事节奏。
- 分辨率按总像素量 `0.4MP/0.7MP/1.0MP` 与画幅计算，并取 32 的倍数；不是固定 720p 或 1080p。实际尺寸和片长用媒体文件核实。
- `generateAudio=false` 不连接最终输出音轨，不代表省去联合采样。不要据此保证提速。视频参考的音轨目前没有接入图；需声音参考时单独提取、挂载并说明用途，或后期保留原音轨。

预览调试的档位选择、串行迭代和交付复核见 [0.4MP 快速调试](../08-toonflow-generation.md#用-04mp-快速调试)。

## 两段视频怎么衔接

默认在分镜时设计切镜：前段的可剪出点与后段第一镜共同决定观感。前段人物中景收尾，后段可从对手反应、道具细节、不同景别或不同角度介入；仍须保持视线、轴线、持物和动作阶段。后段正文直接写切后第一镜的构图，不把“跨文件切镜”误写成生成转场特效。具体设计见 [分镜与镜序](../06-storyboard.md#跨生成段的剪辑接口)。

确需同一个人接着完成同一动作时，使用上一段采用切点之前的最后 **22 帧**作为独立视频参考：

1. 检查实际 take，选定可用切点，按解码帧准确截取截至该点的 22 帧；不足 22 帧时如实报告，不重复帧伪装。若采用整段结尾，就是文件最后 22 帧。
2. 当前 H3 输出 24 fps，22 帧约 0.917 秒。另存片段，保留原片，记录来源与帧范围。可用 FFmpeg 的 `trim=start_frame=S:end_frame=E,setpts=PTS-STARTPTS`（E 不含，E-S=22）并重新编码；不用可能偏到关键帧的流复制裁切。不同帧率来源需核对重采样后的实际输入，不能把 22 帧直接写成固定秒数。
3. 适配器会重采样到 24 fps，先载入视频开头，再只取前 48 帧，H3 条件按 `17n+5` 帧处理；22 帧可完整进入条件。因此挂裁好的尾部片段，不能挂整段原片期待它自动读结尾。
4. 把它绑定为 `<Video N>`，提示词交代“从这段参考末尾状态继续”，并写清人物、视线、持物手、接触位置、动作方向、速度和接下来的变化；不要重新演参考里的动作。完整人物与场景图仍按需保留，不强制再加尾帧图片。
5. 参考只引导连续性，不保证姿态或像素完全一致。出片后对照两侧动作与声音，优先用可用区间、切点或声音桥缓解差异；做不到已定连续动作才返工。

## 超时、停止和恢复

记录 Toonflow 的 requestId 与 ComfyUI prompt_id/taskId。超时先查原队列、历史和已有输出；适配器能按已有 ID 恢复查询，状态不明时不重新提交。服务已完成但画布未收回时先收回原产物。

前端重连或刷新后，重新读取 `getAppState`，定位原项目、画布和节点，再对照任务记录与输出文件。节点回到空闲状态不等于原任务失败，不能据此直接补跑。

Toonflow 的停止可能只停止等待，ComfyUI 仍会运行。收到停止要求后核对原任务在队列中的状态；只有确认目标是该任务时才取消。全局 interrupt 可能影响其他任务，不能当作按 ID 取消。记录最后状态，避免紧接着重投造成重复任务。
